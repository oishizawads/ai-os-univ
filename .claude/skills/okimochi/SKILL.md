# okimochi / お気持ち

## When to use

ユーザーが作業中に「お気持ち」という言葉を使ったとき。このスキルは、その曖昧な指示を文脈に応じて解釈する。

「お気持ち」は一義的な定義を持たない。**文脈によって、以下のどれか（複数可）を指す。**

## Three modes of "お気持ち"

### 1. 体裁・プロトタイプ優先モード

> 「正確性・完全性よりも、見た目・雰囲気・第一印象・プロトタイプ的な形」を優先する。

- 裏側が定数の `print` でも、見た目がダッシュボードならOK
- 内容の網羅性より、読み手に伝わる構成を優先
- 完璧なエラーハンドリングより、まず動くものを素早く作る

### 2. 社交辞令・機嫌取りモード

> 相手を喜ばせる・安心させる・受け入れてもらうための表現を優先する。

- 「相手の機嫌をとるトーク」
- 「熱く夢を語る」ピッチ
- 批判や欠点より、期待や可能性を前面に出す
- 相手の立場や感情に配慮した言い回し

### 3. ビジコン・熱意重視モード

> 実現性・厳密性は一旦脇に置き、熱意・ビジョン・社会性・ストーリーを重視する。

- 実現性は「さておき」、夢や社会貢献を語る
- 数字よりイメージ、分析より物語
- 「なぜやるか」「どう変えるか」を強調
- 聞き手を巻き込む感情的な訴求

---

## How to detect which mode

| 文脈 | 解釈 |
|------|------|
| 「お気持ちダッシュボード」 | モード1：体裁・プロトタイプ優先 |
| 「お気持ちの提案書」 | モード1 or 2：読みやすさ・相手に響く構成 |
| 「お気持ちで実装して」 | モード1：まず動くものを素早く |
| 「この要件お気持ちで作って」 | モード1：展示会・営業デモ用の見た目重視プロトタイプ |
| 「お気持ちUIで」 | モード1：第一印象・操作性を重視したUI |
| 「お気持ちトーク」 | モード2：社交辞令・機嫌取り |
| 「ビジコンはお気持ち界隈」 | モード3：熱意・夢・ストーリー重視 |
| 「お気持ちじゃなくて本当に見てほしい」 | **お気持ちモードOFF**：厳密性・実現性を重視 |

## How to respond

### モード1（体裁・プロトタイプ）の場合

1. 形を先に作る。完璧を目指さない。
2. 過度な検証を避ける。テスト・型チェックは後回し。
3. 拡張しやすい構造にする（定数は上部にまとめるなど）。
4. 安全・倫理・法的リスクだけは確認する。
5. すぐにユーザーに見せてフィードバックを取る。

#### 展示会・営業デモ向けの追加ルール

- **15分で動くものを作る**：顧客が目の前にいる想定で、見た目・操作性・レスポンスを最優先。
- **顧客の用件メモをそのままUIに落とす**：名詞・数字・画面遷移を素早く形にする。整合性の検証は後。
- **お気持ちUIで釣る**：グラフやアイコン、アニメーション、ダークモードなど、素人が「かっこいい」と感じる要素を入れる。
- **デモ用データはハードコード・モックでOK**：API連携やDBは後で差し替えられる形にする。
- **「これはデモ版です」と明示する**：本番同等を装わず、今後の拡張可能性を語る余白を残す。

### モード2（社交辞令・機嫌取り）の場合

1. 相手の立場・感情・関心事を先に把握する。
2. 批判や欠点は後回し、まず共感・感謝・期待を伝える。
3. 「○○のおかげで」「○○に感謝」など、相手を評価する表現を入れる。
4. 結論や要求は、相手にメリットがある形で述べる。
5. 建前としての体裁は保ちつつ、ユーザーが本当に伝えたい核心は損なわない。

### モード3（ビジコン・熱意重視）の場合

1. なぜこのプロジェクトが大切か、をストーリーで語る。
2. 数字や実現性は「検証予定」「PoCで確認」として、夢を壊さない形で補足。
3. 社会貢献・将来像・変化のイメージを強調。
4. 聞き手が「応援したい」と思える言い回しを使う。
5. 熱意が空回りしないよう、具体例やエピソードで支える。

## What NOT to do

- 「お気持ち」を「適当でいい」と解釈しない。
- 相手の機嫌を取るあまり、嘘や約束できないことを言わない。
- ビジコン用の熱意表現が、社内の技術レビュー資料に混ざらないよう区別する。
- デモ用の「お気持ちUI」を本番導入の品質基準と混同しない。
- ユーザーの意図を勝手に矮小化しない。
- 後で取り返しのつかない作り込み（ハードコーディングした値を多数の場所に埋め込むなど）は避ける。
