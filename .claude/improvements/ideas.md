# workspace 運用改善アイデア集

> 生成元：Claude Code との対話（2026-06-21）
> 対象：8層パイプライン・Claude 直接実行・decision-lab・品質ゲートを前提とした workspace 全体の改善
> 運用：月次レビューで見直し。アイデアを無理に全部導入せず、最小構成から試す。

---

## 背景

現状の workspace は「タスクを正しく処理するマシン」としては高い完成度がある。

- 8層パイプラインでタスクを位置づける
- Claude 直接実行を原則とし、必要なら OpenCode / Gemini / Codex へ委譲
- decision-lab で分析の並列検証
- stop-slop / ui-polish / ship-harden で品質管理
- result.md / SESSION_NOTES.md / decisions/ / failure_patterns/ で記録
- PARA / Evergreen / memory/ で知識管理

一方で、「長期間高いパフォーマンスを出し続ける人間」側の支援が弱い。
このファイルは、メタ認知的に導出した改善アイデアを貯める場所。

---

## 現状の強み

| 領域 | 状態 |
|---|---|
| タスクの位置づけ | 8層パイプラインでカバー済み |
| AI 出力の検証 | decision-lab / 2経路突き合わせでカバー |
| 品質管理 | stop-slop / ui-polish / ship-harden でカバー |
| 記録 | SESSION_NOTES / result.md / decisions/ / failure_patterns/ でカバー |
| 知識管理 | PARA / Evergreen / memory/ でカバー |
| 経済性・倫理法務 | 横断軸として定義済み |

## 現状の弱い領域と改善アイデア

### 1. タスク状態の可視化・滞留管理

**問題：** タスクがどの層で止まっているか、週に何をこなしたかが見えにくい。

**アイデア：**
- 週次ダッシュボードを作る
- 各タスクの 8層上の位置を可視化
- 滞留タスクに警告を出す
- 完了率・種別の統計を取る

**実装案：**
- `life/task-board.md` または `ai-os/task-board.md` を作る
- 日曜の週次計画時に更新
- 各行：タスク名 | 8層の位置 | 次のアクション | 滞留日数

---

### 2. 信念・判断の追跡（Belief Tracking）

**問題：** 「決定事項」は残るが、「なぜそう決めたか」「当時の確信度」が消える。

**アイデア：**
- 判断ごとに確信度・根拠・反対証拠・リスクを記録
- 後から「この判断は正しかったか」を振り返る

**実装案：**
- `decisions/` に `YYYYMMDD_decision_name.md` を統一フォーマットで作成
- テンプレート：
  - 判断
  - 確信度（1-5）
  - 根拠
  - 反対証拠
  - リスク
  - 3ヶ月後の検証結果

---

### 3. Pre-mortem の自動支援

**問題：** 重要タスクの前に失敗シナリオを考えるのは強力だが、手動だとサボる。

**アイデア：**
- 新タスクを入力すると、過去の `failure_patterns/` から類似パターンを引っ張ってくる
- 「このタスクは過去の X に似ている。注意点は...」

**実装案：**
- `failure_patterns/` にタグをつける
- 新タスクのキーワードで類似検索
- 簡易 RAG でも可

---

### 4. エネルギー・コンディション管理

**問題：** タスク管理だけではなく、自分の燃料ゲージが見えないと燃え尽きる。

**アイデア：**
- 朝のコンディションを記録（睡眠・モチベーション・疲労 1-5）
- コンディションに応じたタスク難易度の提案
- 週のエネルギー消費を可視化

**実装案：**
- `life/health.md` にコンディション欄を追加
- または `life/condition.md` を新設
- 日曜計画時に「今週のエネルギー予算」を設定

## メタ認知的まとめ

現状の workspace は「タスクを正しく処理するマシン」としては完成度が高い。
次に強化すべきは「人間が長期間高いパフォーマンスを出し続ける」側。

追加機能の方向性：
- **マシン部分**：すでに十分。細かい自動化は後回しでよい。
- **人間部分**：燃料管理・機会費用の可視化・判断の質・失敗パターンの再利用。

無理に全部導入せず、最小構成から始めて効果を検証する。
