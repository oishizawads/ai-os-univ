## 擁護の基本方針

65個を平等には推さない。良い擁護は無慈悲な選別から始まる。

- **採用基準**：①複利で効く ②既存 workflow に寄生でき新規コードがほぼ要らない ③コストの実体が「実装」でなく「習慣」 ④東大・一橋／キャリア／持続可能性のいずれかに直結。
- **先回りした統合**：Codex の「ファイルが増えすぎる」批判を潰すため、65個を約10テーマに束ねた（例：判断追跡=#2+#42+#56、コンディション=#4+#28+#64、人間関係=#29+#32+#34+#35、週次=#9+#22）。
- **最初から捨てるもの**：#26 目の体操 / #27 ストレッチ / #50 ランダム入力 / #53 振り返り動画台本 / #1 専用ダッシュボード / #52 ICS解析タイムライン / #25 経理フル自動化。これらは workspace 機能ではなく OS リマインダーか、実装コストが効果を上回る。**私はこれらを擁護しない。**

ideas.md 自身の自己診断が正しい：機械側（タスク処理）は完成、ボトルネックは人間側（スループット・判断品質・燃え尽き）。よって火力は人間側に集中する。

## 2. 統合案 — 最初の2週間で導入すべき3つ

増やしすぎると管理コストが勝つ。**新規コード不要・1分/日以下・既存ファイル拡張のみ**の3つに絞る。

1. **やらないこと/機会費用リスト**（#5+#41）— *流入を絞る*
2. **コンディション記録**（#4）— *燃料を測る*
3. **SESSION 引継ぎ欄**（#15）— *セッション間で複利を効かせる*

### なぜこの3つを組み合わせると効くか

3つで「**入力制御 → 容量把握 → 継続性**」の閉ループになる。

```
   #5 やらないこと        #4 コンディション        #15 引継ぎ欄
   （何を入れないか）  →  （どれだけ動けるか）  →  （次にどう繋ぐか）
        ↑__________________ 週次レビューで一括点検 __________________↓
```

- **負荷(#5)と容量(#4)を同時に見て初めて持続可能性が判断できる。** 片方だけでは「頑張れば回る」錯覚に陥る。
- **3つとも週次レビュー（既存 `/weekly-review`）に相乗りさせ、独立した日課を作らない。** 習慣が死ぬのは「新しい儀式」にしたとき。寄生させれば運用コストは実質ゼロ。
- すべて可逆・低リスク。2週間トライ → `experiments.md` に観察を残す（README の運用ルール準拠）。失敗しても `rejected.md` に理由が残り資産化する。

### 3週目以降の追加順

定着を確認してから **判断追跡(#2)**（価値は最上位だが習慣強度が要るのでここに置く）→ **Pre-mortem(#3)** → **週次レビューの本格活用(#6)** の順。

## 3. Codex への反論用メモ

Codex が「コストが…」と来たときに使う5本。

1. **「実装コストが高い」へ** — 私の Top 群は新規コード・新ツールをほぼ要さない。既存資産の拡張（`SESSION_NOTES` に1欄、`failure_patterns` にタグ、`/weekly-review` を起動、`decisions/` にテンプレ）か md 1枚の新設のみ。コストの実体は「実装」でなく「習慣」。重い実装版（RAG・専用ダッシュボード・ICS解析・経理フル自動化）は**私も切っている**。批判対象と推奨対象がずれている。

2. **「メンテナンス負担が大きい」へ** — 推奨は意図的に低頻度・低摩擦に設計済み。日次は30秒〜1分（#4/#15）、人生KPI/年次レビューは月次/年次でメンテ総量は年数回。しかも全部を週次レビューに寄生させ運用儀式を増やさない。メンテが重いのは私が**落とした**アイデア（#1 ダッシュボード・#52 タイムライン・#25 経理）の方。

3. **「ROIが見合わない」へ** — ROIは平均でなく**分散**で見るべき。判断追跡(#2)・Pre-mortem(#3)・やらないこと(#5)はテールリスク（不可逆な誤判断・燃え尽き・機会費用の取りこぼし）を削る保険。発生頻度は低いが、重い誤判断を1回防げば案件単位・数十時間単位の損失を回避する。期待損失への寄与で評価せよ。

4. **「習慣は続かない／即効性がない」へ** — だから最小3つに絞り、すべて既存ルーチンに寄生させ新しい日課を作らない。続かないのは独立儀式にしたとき。さらに「2週間トライ→experiments.md で観察→ダメなら rejected.md」という安全弁が README に既にある。続かないこと自体が観測でき、失敗も資産になる設計。

5. **「機械側は十分、人間側支援は曖昧で測れない」へ** — ideas.md 自身が機械側完成を認めており、次の制約は人間のスループットと判断品質。そこがボトルネックである以上、限界効用は人間側が高い。測定も可能：週次レビュー所要時間／滞留タスク数／コンディション平均／判断追跡の事後検証ヒット率。曖昧なのは指標未定義のアイデア（健康相関分析等）であって、**推奨群はすべて観察可能**。

## まとめ

- 火力を集中すべきは人間側（判断品質・燃料・流入制御）。
- 最強の擁護は選別と統合：65→Top10→**最小3つ（#5/#4/#15）**。
- 3つは閉ループを作り、既存の週次レビューに寄生し、新規コードゼロ。Codex の主要批判（コスト・メンテ・ROI）はこの設計で大半が無効化される。
