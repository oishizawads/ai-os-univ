# データ集約システムのトレードオフ — 分散システム設計フレームワーク

> 出典: Martin Kleppmann『Designing Data-Intensive Applications』
> 用途: 分散システム・データベース・ストレージの設計判断

---

## 0. 根本原則

```
分散システムには銀の弾丸はない。
あらゆる設計は「トレードオフ」の連続であり、文脈に応じて最適解が変わる。
```

- **信頼性（Reliability）**: 故障があっても正しく動く
- **拡張性（Scalability）**: 負荷が増えても性能を維持する
- **保守性（Maintainability）**: 運用・改修が容易

## 1. データモデルの選択

| モデル | 強み | 弱み | 向くケース |
|--------|------|------|-----------|
| **リレーショナル** | 結合、複雑なクエリ、整合性 | スキーマ変更、水平分散 | 構造が明確で、整合性が重要 |
| **ドキュメント** | 柔軟なスキーマ、親子の入れ子 | 結合が苦手、重複データ | 読み取り重視、スキーマが変わりやすい |
| **グラフ** | 複雑な関係性の表現 | 単純な集計が苦手 | ソーシャルグラフ、推薦エンジン |

---

## 2. 分散システムの3つのトレードオフ

### CAP定理の誤解を正す

CAPは「3つ中2つ選ぶ」という単純な分類ではない。実際の設計はより細かい。

| 特性 | 説明 | トレードオフ |
|------|------|-------------|
| **一貫性（Consistency）** | 全ノードが同じデータを見る | 可用性・レイテンシとのトレード |
| **可用性（Availability）** | 全リクエストが応答を得る | 一貫性とのトレード |
| **分断耐性（Partition Tolerance）** | ネットワーク分断に耐える | 分散システムでは避けられない（必須） |

### PACELC定理（実用的な分類）

```
分断時（P）: Availability vs Consistency を選ぶ
通常時（E）: Latency vs Consistency を選ぶ
```

- **AP（可用性重視）**: Cassandra, DynamoDB（ eventual consistency ）
- **CP（一貫性重視）**: HBase, Redis Cluster（ strong consistency ）
- **EL（レイテンシ重視）**: キャッシュ、CDN
- **EC（一貫性重視）**: 分散トランザクション

## 3. レプリケーションとパーティショニング

| 手法 | 目的 | 注意点 |
|------|------|--------|
| **リーダー・フォロワー** | 読み取りスケール | レプリケーション遅延（一貫性の問題） |
| **マルチリーダー** | 地理分散・書き込みスケール | 衝突解決が複雑 |
| **リーダーレス** | 高可用性 | 読み取り修復、クオラムの設計 |
| **シャーディング** | データ量スケール | シャードキーの選定、再バランシング |

## 4. チェックリスト

### データ設計の前に

```
[ ] データモデルは「読み書きのパターン」に最適化されているか？
[ ] 一貫性の要求レベルは「強い一貫性」か「結果整合性」か？
[ ] システムは「CP」「AP」「EL」「EC」のどれに近いか？
[ ] レプリケーション遅延が許容範囲内か？
[ ] シャードキーは「アクセスパターンに偏りがない」ものか？
```
