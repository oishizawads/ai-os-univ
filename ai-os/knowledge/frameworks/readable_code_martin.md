# クリーン・コード — 可読性重視のコーディング規約

> 出典: Robert C. Martin『Clean Code』
> 用途: 保守可能なコードの書き方、チーム開発での可読性向上

---

## 0. 根本原則

```
コードは「動く」だけでは不十分。コードは正しく、かつ読みやすくなければならない。
読みやすさ = 保守性 = 変更コストの低さ
```

- **コードは意見の表明**: 作者の「意図」を正確に伝える責任がある
- **Boy Scout Rule**: コードを触れたら、必ず元よりきれいにして去る
- **DRY**: Don't Repeat Yourself。同じ知識を2箇所で持たない

---

## 1. 命名（Naming）

| 原則 | 悪い例 | 良い例 |
|------|--------|--------|
| **意図が明確** | `d` | `elapsedTimeInDays` |
| **嘘をつかない** | `accountList`（実際は配列ではない） | `accounts` |
| **発音可能** | `genymdhms` | `generationTimestamp` |
| **検索可能** | `e`（1文字変数） | `error` |

---

## 2. 関数（Functions）

- **小さく**: 20行を超えるなら分割を検討する
- **一つのことだけ**: 関数は「1つのことを」「それを正しく」「ただそれだけを」行う
- **引数は少なく**: 理想は0、1は可、2は注意、3は避ける
- **副作用なし**: 関数は「問い」（値を返す）か「命令」（何かを変更する）のどちらか。
  両方を同時にやらない。

---

## 3. コメント（Comments）

```
最良のコメントは、コメントを書かないこと。
コード自身が「意図」を語るべきである。
```

- **良いコメント**: 法的な理由、TODO（ただし速やかに対応）、警告
- **悪いコメント**: コードと矛盾するコメント、冗長な説明、履歴（Gitに任せる）

---

## 4. チェックリスト

### コードレビュー前に

```
[ ] 変数名・関数名は「発音可能」で「検索可能」か？
[ ] 関数は20行以内で、「1つのことだけ」をしているか？
[ ] 引数の数は3個以内か？
[ ] コメントがコードの「意図」を補足しているか、それとも「説明」になっているか？
[ ] 同じロジックが2箇所以上に書かれていないか（DRY）？
[ ] このコードを触ったら、元よりきれいにできたか（Boy Scout Rule）？
```

---

## Claude に適用する場合のプロンプト冒頭

```
Clean Codeの原則に従って、コードをレビュー・改善してください。
1. 変数名・関数名が「意図を明確に伝える」名前になっているか確認する
2. 関数は「小さく」「1つのことだけ」を行うように分割する
3. 引数の数を減らし、副作用を排除する
4. 「コメントで説明している」部分を、コード自身で語る形にリファクタリングする
---
[レビュー対象のコードをここに記述]
```
