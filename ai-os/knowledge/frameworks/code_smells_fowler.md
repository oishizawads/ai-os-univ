# コードの臭い（Code Smells）— リファクタリング判断フレームワーク

> 出典: Martin Fowler『Refactoring』
> 用途: いつリファクタリングすべきかの判断、技術的負債の早期発見

---

## 0. 根本原則

```
リファクタリングとは、外部の振る舞いを変えずに、内部構造を改善すること。
「後でやる」は永遠に来ない。臭いを嗅いだら、今すぐ手を付ける。
```

- **コードの臭い（Code Smell）**: バグではないが、深い問題を示唆する構造上の特徴
- **リファクタリングのトリガー**: 新機能追加前、バグ修正時、コードレビュー時
- **安全網**: リファクタリング前にテストを書く。テストが通らなければ巻き戻す。

---

## 1. 主要なコードの臭い

| 臭い | 症状 | 対処法 |
|------|------|--------|
| **長い関数** | 1つの関数が複数の責務を持つ | 関数の抽出（Extract Function） |
| **巨大なクラス** | 1つのクラスが多すぎるメソッド・変数を持つ | クラスの抽出、責務の分離 |
| **重複したコード** | 同じロジックが2箇所以上にある | メソッドの抽出、共通化 |
| **長い引数リスト** | 関数の引数が4つ以上 | 引数オブジェクトの導入、コンテキストオブジェクト化 |
| **散在した変更（Shotgun Surgery）** | 1つの変更をするために多数のクラスを触る | 関連する責務を1つのクラスに集める |
| **特性の羨望** | クラスAがクラスBのデータを多用する | メソッドの移動（A→B） |
| **switch文/型による条件分岐** | 同じ条件分岐が複数箇所にある | ポリモーフィズム、Strategyパターン |

---

## 2. リファクタリングの手順

1. **テストを書く（または確認する）**: 変更前に既存の振る舞いを担保するテストがあることを確認
2. **小さく変更する**: 一度に大きな変更をしない。コンパイルエラーを最小限に
3. **テストを実行する**: テストが通ることを確認
4. **次の臭いへ**: 1つ解決したら次に進む。完璧を目指さない

---

## 3. リファクタ vs 再設計

| | リファクタリング | 再設計 |
|---|----------------|--------|
| **外部振る舞い** | 変えない | 変える可能性がある |
| **リスク** | 低い（テストで担保） | 高い |
| **規模** | 小さく継続的 | 大きく一度きり |
| **タイミング** | 常に（機能追加の前後） | 限定的（技術的負債が限界に近い時） |

---

## 4. チェックリスト

### コードを触る前に

```
[ ] このコードに「臭い」はないか？（長い関数、重複、巨大なクラスなど）
[ ] リファクタリング前に、既存の振る舞いを担保するテストはあるか？
[ ] 今回の変更は「外部振る舞い」を変えないか？
[ ] 一度に大きな変更をしていないか？（小さくステップを踏んでいるか）
[ ] リファクタリングと「新機能追加」を同時に行っていないか？
```

## Claude に適用する場合のプロンプト冒頭

```
リファクタリングの観点でコードを分析・改善してください。
1. コードの「臭い（Code Smells）」を特定する（長い関数、重複、巨大なクラスなど）
2. 特定した臭いに対し、具体的なリファクタリング手法（Extract Method, Move Method など）を提案する
3. 変更前に「外部振る舞いを変えない」ことを担保するテスト戦略を示す
4. リファクタリングと「新機能追加」を混同しないよう、変更の範囲を明確にする
---
```
