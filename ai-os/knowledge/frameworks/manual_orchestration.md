# Manual Orchestration Framework

> 4画面手動運用の理論・原則・失敗パターン。システム化の罠を避けるための指針。
>
> **Status (2026-06-21): 原則は現行・ツール詳細は一部 legacy。** モデル名（Opus 4.7 / Sonnet 4.6 等）と `/dispatch` は当時の記録（履歴証拠として残置）。現行の委譲は直接コマンド（`/opencode-coder` / `/gemini-coder` / `/codex-coder`）＋ `/codex:rescue`。正典は root `CLAUDE.md`。

---

## 結論

**システム化より、人間（Claude）がオーケストレーターになる方が圧倒的に現実的。**

- 自動化パイプラインは「想定外のケース」で破綻する
- 人間の判断（特にプロンプト品質の微調整）は自動化できない
- 4画面開いて手動で回す方が、結果的に早く・確実に・安く済む

---

## なぜシステム化が失敗するか

### 1. プロンプト品質の問題

自動化パイプラインの弱点：
- タスク分解の品質が機械的になりがち
- 各モデルへのプロンプト最適化ができない
- コンテクストの取捨選択が荒い

人間（Claude）の強み：
- タスクの本質を理解して最適な分解ができる
- 各モデルの癖を理解したプロンプトを書ける
- 必要に応じてリアルタイムで微調整できる

### 2. エラーハンドリングの問題

自動化パイプラインの弱点：
- エラー時の原因特定が困難（どのSubで落ちたか分からない）
- フォールバック戦略が単純すぎる
- 無限ループに陥るリスク

人間（Claude）の強み：
- エラー出力を読んで判断できる
- 適切なフォールバックを選択できる
- 無限ループを未然に防げる

### 3. コスト最適化の問題

自動化パイプラインの弱点：
- Opus 4.7を使いすぎる（高価なモデルが自動選択される）
- 軽量タスクも重いモデルで処理される
- 予算超過が分かりにくい

人間（Claude）の強み：
- タスクを見て「これはOCで十分」と判断できる
- リアルタイムでコストを監視できる
- モデル間の使い分けが最適化できる

## 手動運用の原則

### Principle 1: CCは司令塔

- CC（Claude Code）がタスク分解・プロンプト生成・結果統合を行う
- CC自身は実装を**絶対に**行わない
- 実装は常にSub（CX/GM/OC）に委譲

### Principle 2: プロンプトはCCが作る

- 人間はタスク内容を伝えるだけ
- CCが各Sub向けの最適化プロンプトを生成
- 人間はコピペするだけ（改変禁止）

### Principle 3: 無制限モデルを優先

- Gemini（$20/月、無制限に近い）→ 調査・分析・軽量レビュー
- OpenCode Go（$10/月、無制限に近い）→ 軽量実装・並列生成
- Codex（$20/月、週次100%残存）→ 重要実装・レビュー
- Claude（$20/月、Opusは限定的）→ 設計・戦略・最終判断のみ

### Principle 4: 記録は必須

- コスト追跡：各タスクのコストを記録
- 品質追跡：/feedback で各モデルの品質を記録
- 週次集計：feedback_analyzer.py で傾向分析

### Principle 5: フィードバックループ

- 週次で「どのモデルがどのタスクで得意/不得意だったか」を振り返る
- プロンプトテンプレートを改善
- ルーティング戦略を更新

## 画面配置のベストプラクティス

### 推奨レイアウト

```
┌─────────────────┬─────────────────┐
│   Main (CC)     │   Sub1 (CX)     │
│  オーケストレータ  │  重い実装・レビュー │
├─────────────────┼─────────────────┤
│   Sub2 (GM)     │   Sub3 (OC)     │
│  調査・分析       │  軽量実装・並列   │
└─────────────────┴─────────────────┘
```

### ターミナルマルチプレクサの使用

- **Windows**: Windows Terminal（ペイン分割）
- **Mac**: iTerm2 または tmux
- **Linux**: tmux または screen

### ペイン分割コマンド例（tmux）

```bash

tmux split-window -v
tmux select-pane -t 0
tmux split-window -v
```

## モデル別の特性と活かし方

### Claude Code（CC / Sonnet 4.6）

- **強み**: 設計・タスク分解・統合・判断
- **弱み**: コスト（$20/月、Opusは高価）
- **活かし方**: 司令塔として常に動かす。実装は絶対にさせない。
- **注意**: Opus 4.7は週2〜3回まで。それ以上はSonnetで代替。

### Codex（CX / GPT-5.4）

- **強み**: 実装品質・セキュリティレビュー・複雑リファクタ
- **弱み**: コスト（$20/月、従量課金）
- **活かし方**: 重要実装・レビューにのみ使用。軽量タスクはOCで。
- **注意**: 週次使用量を監視。100%残存なので今は豊富。

### Gemini（GM / 2.5 Pro）

- **強み**: 無制限に近い・調査・長文脈・マルチモーダル
- **弱み**: 指示追従が不安定・品質ブレがある
- **活かし方**: 調査・分析・軽量レビューに全力。プロンプトは具体的に。
- **注意**: 出力が変なときはプロンプトを修正。それでもダメならCX/OCへ。

### OpenCode Go（OC / GLM-5.1）

- **強み**: 最安・無制限に近い・軽量実装に十分
- **弱み**: 設計・複雑推論には不向き・品質は最上位ではない
- **活かし方**: 軽量実装・スニペット・並列生成・フォールバック
- **注意**: 重要コードはOCで実装後、CXでレビューする流れにする。

## 失敗パターン（教訓）

### パターンA: CCに実装させる

**症状**: CC（Claude）に直接実装させてしまい、コストが爆発。

**原因**: 「Claudeが一番賢いから」という安直な発想。

**対策**: CCは司令塔のみ。実装はSubへ。

### パターンB: プロンプトを手動で改変

**症状**: CCが生成したプロンプトを人間が「ちょっと直して」投入 → 結果が悪化。

**原因**: 人間がモデルの特性を理解していない。

**対策**: CCのプロンプトはそのままコピペ。改変禁止。

### パターンC: 全タスクをCX（Codex）で処理

**症状**: 軽量タスクもCodexで処理 → 予算超過。

**原因**: Codexが便利すぎて使いすぎる。

**対策**: 軽量タスクはOCまたはGM。Codexは重要タスクのみ。

### パターンD: 記録を怠る

**症状**: 「あのタスクどのモデルでやったっけ？」→ 同じ失敗を繰り返す。

**原因**: フィードバックループを回していない。

**対策**: /feedback 必須。週次で集計。

## 成功パターン

### パターンX: 調査→設計→実装→レビュー

1. **GM** で調査（無制限なので深く掘れる）
2. **CC** で設計（GMの調査結果を基に最適な設計を判断）
3. **CX** で実装（重要コードはCodexで品質担保）
4. **CC** で統合・最終レビュー

**コスト**: GM（安）+ CC（中）+ CX（高）→ 適切に使い分けている

### パターンY: 軽量実装の並列生成

1. **CC** で「3つの実装案を並列で作って」と指示
2. **OC** × 3画面で同時実行（同じプロンプトを3回投入）
3. **CC** で「3つの案を比較して最適なものを選んで」

**コスト**: OC（最安）× 3 → 並列で時間短縮
