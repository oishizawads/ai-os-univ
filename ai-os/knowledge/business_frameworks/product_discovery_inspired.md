# プロダクト・ディスカバリー — 顧客価値検証フレームワーク

> 出典: Marty Cagan『Inspired: How to Create Tech Products Customers Love』
> 用途: 不確実性の高い機能開発前の顧客課題理解と仮説検証

---

## 0. 根本原則

```
「顧客が愛するプロダクト」を作るには、コードを書く前に顧客の問題を深く理解し、
解決策の仮説を迅速に検証する。
```

- **仮説駆動**: 解決策を確定事実ではなく仮説として扱う。成功するチームはビルド前にアイデアの大部分を破棄している。
- **リスク先行**: 顧客価値、ユーザビリティ、技術実行可能性、ビジネス収益性の4リスクを、開発前に理解する。

---

## 1. 4つのリスク

| リスク | 問い |
|--------|------|
| **価値** | 顧客がこれを本当に欲しいか？ |
| **ユーザビリティ** | 使い方を理解できるか？ |
| **実行可能性** | チームが作れるか？ |
| **ビジネス収益性** | ビジネスモデルとして成立するか？ |

---

## 2. 実践ステップ

### Step 1: 顧客の問題を理解する
- ユーザーインタビュー・観察で「現在の行動と痛点」を記録する
- 「顧客が本当に解決したいこと（Job-to-be-Done）」を1文で定義する

### Step 2: 解決策の仮説を立案する
- PM・デザイナー・エンジニアの3人組で複数の解決案を並列検討する
- 1案に固定せず、4リスクを列挙して比較する

### Step 3: プロトタイプで検証する
- **最もリスクが高い仮説から先に検証する**
- プロトタイプの忠実度をリスクに合わせる：
  - 価値リスク → 偽のドアテストや販売ピッチ
  - ユーザビリティリスク → インタラクティブプロトタイプ（Figma等）
  - 技術リスク → スパイク実装
- 顧客に見せて反応を観察し、仮説を「破棄・修正・前進」で判断する

### Step 4: 確度の高い機能定義へ移行
- 4リスクが十分に下がったら、エンジニアリングへ「顧客の問題」と「検証された仮説」を引き渡す
- 引き渡しは「要件定義書」ではなく「検証済みの学び」として行う

---

## 3. よくある失敗

- **ビルドしてから評価**: 「とりあえず作ってみよう」は失敗。作ると心理的に破棄しにくくなる（コンコルド効果）。
- **PMだけで考える**: エンジニア・デザイナーを関与させず、PRDを投げるだけでは解決策の品質が下がる。
- **顧客の要望をそのまま実装**: 顧客は本当の問題を言語化できないことが多い。「要望＝解決策」ではない。
- **完璧なプロトタイプを作りすぎる**: 数日で破棄される可能性がある。検証に必要な最低限の品質で十分。

---

## 4. チェックリスト

### 開発着手前に

```
[ ] 顧客インタビューや観察を実施したか？
[ ] 解決策を1つに絞らず、複数の仮説を並列で検討したか？
[ ] コードを書く前に、プロトタイプやテストで顧客に検証したか？
[ ] 4リスクのうち、最も高いリスクから先に検証したか？
[ ] 検証結果に基づき、想定していたアイデアを破棄できたか？
[ ] エンジニア・デザイナーがディスカバリー活動に参加したか？
```

## Claude に適用する場合のプロンプト冒頭

```
プロダクト・ディスカバリーの考え方で提案してください。
1. 顧客の「本当の問題（Job-to-be-Done）」を特定する
2. 解決策を1つに絞らず、複数の仮説を並列で立案する
3. 最もリスクが高い仮説から、最小コストで検証する方法を考える
4. 検証結果に基づき、「破棄・修正・前進」を判断する基準を示す
---
[本題をここに記述]
```
