# リーン・スタートアップ — 事業開発・PMフレームワーク

> 出典: エリック・リース『リーン・スタートアップ』
> 用途: 不確実性の高い状況での製品開発、無駄の排除、高速な学習

---

## 0. 根本原則

```
構築(Build) → 計測(Measure) → 学習(Learn) のループを最速で回す
```

- **目的**: 何を作るべきか（何が顧客に価値をもたらすか）を、最小限のコストで科学的に突き止める。
- **検証による学習**: 計画通りに進むことよりも、現実のデータから学ぶことを重視する。

---

## 1. 3つの重要概念

### MVP (Minimum Viable Product)
実証済みの学習（顧客の反応）を得るために必要な、最小限の機能を備えた製品。
- 完璧を目指さず、**「学習のための道具」**として割り切る。

### 検証による学習 (Validated Learning)
「顧客はこう動くはずだ」という仮説を、実際の数値（計測）で裏付けること。
- 虚栄の指標（PVなど）ではなく、実質的な指標（継続率など）を見る。

### ピボット (Pivot) または 辛抱 (Persevere)
計測・学習の結果、戦略を根本から変えるか、そのまま突き進むかの決断。
- 失敗を認めるのではなく、新しい仮説へ移行する。

---

## 2. 実践ステップ

### Step 1: 飛躍の仮説 (Leaps of Faith)
事業の成否を分ける最も重要な仮説を特定する。
- **価値仮説**: 顧客はこの製品に価値を感じるか？
- **成長仮説**: どうやって広まっていくか？

### Step 2: 構築（MVPの作成）
仮説を検証するために必要な、最小限のものを構築する。
- 豪華なUIやバックエンドを実装する前に、ランディングページや手動（コンシェルジュ）で試せないか検討する。

### Step 3: 計測（データ収集）
顧客の行動を客観的な数値で計測する。
- コホート分析などを用い、変更が本当に改善につながったかを確認する。

### Step 4: 学習（意思決定）
計測結果に基づき、戦略を維持するか、ピボットするかを決める。

---

## 3. ピボットの種類（代表例）

| 種類 | 内容 |
|-----|------|
| **ズームイン・ピボット** | 単一の機能が製品全体になる |
| **ズームアウト・ピボット** | 製品全体が、より大きな製品の一機能になる |
| **顧客セグメント・ピボット** | 製品は変えず、ターゲット顧客を変える |
| **顧客ニーズ・ピボット** | 同じ顧客に対し、別の切実な悩みを解決する |
| **プラットフォーム・ピボット** | アプリケーションからプラットフォーム（基盤）へ変更する |

---

## 4. チェックリスト

### 開発・企画の前に

```
[ ] 検証しようとしている「飛躍の仮説」は何か？
[ ] その検証に、この機能（開発）は本当に必要か？
[ ] もっと安く、早く検証する方法（プロトタイプ）はないか？
[ ] 何を計測すれば、仮説の正否を判断できるか？（具体的な数値目標）
```

## Claude に適用する場合のプロンプト冒頭

```
リーン・スタートアップの考え方で提案してください。
1. まず、このプロジェクトにおける「最も重要な仮説（飛躍の仮説）」を特定する
2. その仮説を最小コストで検証するための MVP（最小機能製品）の構成を考える
3. 「計測」すべき具体的な指標（KPI）を、虚栄の指標を避けて設定する
4. 想定される結果に基づき、どのような場合にピボットを検討すべきか基準を示す
---
[本題をここに記述]
```
