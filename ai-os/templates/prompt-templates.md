# Prompt Templates for Multi-Screen Manual Orchestration

> Copy-paste ready prompts for each Sub model. Generated by CC (Claude) and used as-is.

---

## Template A: Coding Task (Standard)

### For CX (Codex) — Implementation

```
## Context
We are building a {project_name}. This task is part of {module_name}.
Existing code context: {file_paths_or_summary}

## Instruction
Implement the following function/class:
{specification}

Requirements:
- Language: {language}
- Framework: {framework}
- Must include error handling
- Must include docstring
- Must pass these test cases: {test_cases}

## Output Format
Return ONLY the code in a single markdown code block.
Do not include explanations outside the code block.
```

### For GM (Gemini) — Review

```
## Context
This code was implemented by Codex for {project_name}.
Original spec: {specification}

## Instruction
Review the following code for:
1. Correctness (does it meet the spec?)
2. Edge cases (what's missing?)
3. Security issues (if applicable)
4. Performance concerns
5. Style/idiom issues

## Output Format
Return a structured review:
- **Overall**: PASS / NEEDS_FIX / REJECT
- **Issues**: numbered list with severity [critical|major|minor]
- **Suggestions**: specific improvements
- **Missing**: what test cases or edge cases are not covered
```

### For OC (OpenCode) — Lightweight Fallback

```
## Context
Quick implementation needed for {project_name}.

## Instruction
Implement: {brief_spec}
Keep it simple and correct. Do not over-engineer.

## Output Format
Code only in markdown code block.
```

## Template B: Research Task

### For GM (Gemini) — Primary Research

```
## Context
We need to understand {topic} for {purpose}.

## Instruction
Research and summarize:
1. What is {topic}? (definition)
2. Current state of the art (latest developments as of 2026)
3. Key players / tools / libraries
4. Pros and cons of different approaches
5. Recommendations for our use case: {use_case}

## Output Format
Structured report with headers. Include source URLs if possible.
```

### For CC (Claude) — Synthesis

```
## Context
Gemini has researched {topic}. Here are the findings:
{gm_research_output}

## Instruction
Synthesize these findings into actionable recommendations:
1. What should we do? (specific action items)
2. What should we avoid? (anti-patterns)
3. What are the risks?
4. What are the next steps?

## Output Format
Executive summary + detailed recommendations.
```

## Template C: Design Task (Critical)

### For CC (Claude Opus 4.7) — Architecture Design

```
## Context
We are designing {system_name} with these constraints:
{constraints}

## Instruction
Design the architecture:
1. High-level component diagram (text-based)
2. Data flow
3. API boundaries
4. Error handling strategy
5. Scalability considerations

## Output Format
Markdown with diagrams in text/ASCII. Include decision log (why you chose each approach).
```

### For CX (Codex) — Implementation of Critical Parts

```
## Context
Claude designed this architecture:
{cc_design_output}

## Instruction
Implement the most critical/security-sensitive component:
{critical_component_spec}

## Output Format
Code + brief explanation of key decisions.
```

## Template D: Review Task

### For CX (Codex) — Security Review

```
## Context
Review this code for security vulnerabilities:
{code_to_review}

## Instruction
Check for:
1. Injection vulnerabilities (SQL, command, XSS)
2. Authentication/authorization issues
3. Data validation gaps
4. Secrets leakage
5. Dependency vulnerabilities

## Output Format
- **Risk Level**: CRITICAL / HIGH / MEDIUM / LOW
- **Findings**: numbered list with CVE/OWASP references if applicable
- **Fixes**: specific code changes needed
```

### For GM (Gemini) — Logic Review

```
## Context
Review this code for logic correctness:
{code_to_review}

## Instruction
Check for:
1. Logic bugs / edge cases
2. Performance issues
3. Concurrency issues (if applicable)
4. API contract violations

## Output Format
- **Verdict**: PASS / NEEDS_FIX / REJECT
- **Issues**: numbered list
- **Test Recommendations**: what tests should be added
```

## Template E: Refactor Task

### For CC (Claude) — Refactor Plan

```
## Context
This code needs refactoring:
{code_to_refactor}

## Instruction
Create a refactor plan:
1. What's wrong with the current code? (smells)
2. Target architecture
3. Step-by-step migration plan (safe, no breaking changes)
4. Testing strategy during migration

## Output Format
Plan only. Do not write the refactored code yet.
```

### For CX (Codex) — Step-by-Step Refactor

```
## Context
Execute refactor step {N} of the plan:
{refactor_plan}

## Instruction
Apply this specific change:
{specific_change}

## Output Format
Full refactored code + diff summary.
```
